# Arpit Kumar · Portfolio (MERN)

A multi-page portfolio that is also a small data product. Visitors can query it with SQL, open a page for each project, see which skills each project actually uses, and watch the site's own traffic on a live analytics page.

## Pages

| Route | Page |
| --- | --- |
| `/` | Landing: intro, SQL console, selected work, recent experience, most-used tools |
| `/projects` | All projects with category filters |
| `/projects/:slug` | Project write-up with stack, links, related projects and previous/next |
| `/skills` | Skill × project heatmap and skills by category |
| `/experience` | Timeline, certifications, education |
| `/analytics` | Live traffic dashboard and how it works |
| `/posts` | Your LinkedIn posts as official LinkedIn embeds, with “Like on LinkedIn” and “Comment” buttons |
| `/contact` | Contact form and direct links |
| `/admin` | Private, not in the menu: add or remove LinkedIn posts (needs `ADMIN_TOKEN`) |
| anything else | 404 page |

Any query chip on a page opens the console on the landing page with that query (`/?q=…`).

**Stack:** MongoDB · Express · React (Vite) · Node.js

## What's inside

| Feature | How it works |
| --- | --- |
| SQL console (hero) | A tiny SQL engine in `client/src/lib/sql.js` runs `SELECT … FROM projects/experience/certifications/skills WHERE … ORDER BY … LIMIT …` over data served by the API. Try `HELP`. |
| Projects, experience, certifications | Stored in MongoDB, served by `GET /api/content`. Edit `server/src/data/content.js`, then `npm run seed`. |
| Skills, by evidence | A skill × project heatmap computed from each project's stack. |
| Live analytics | The client posts anonymous events (`pageview` with the page path, `query`) to `POST /api/events`; unknown paths are counted as `/404`; `GET /api/stats` aggregates them in MongoDB. No IPs or cookies stored. Events expire after a year. |
| Contact form | `POST /api/contact`, validated, rate-limited (5 per 15 min) and saved to MongoDB, with a honeypot field for bots. |

## Run locally

Needs Node 18.18+.

```bash
npm run setup        # installs root, server and client dependencies
npm run dev          # API on :5000, React on :5173 (proxied)
```

Open http://localhost:5173. Without `MONGODB_URI` the API uses an in-memory store, so it runs with zero setup; data resets on restart.

To use MongoDB, copy `server/.env.example` to `server/.env` and set `MONGODB_URI`. The database is seeded automatically the first time it's empty.

## Preview without a server

`npm run build:demo --prefix client` builds a static copy into `client/dist-demo/` that runs entirely in the browser: content is bundled, analytics are kept in the visitor's own browser, and the contact form explains that messages only send from the real site. Open it with any static file server, for example `npx serve client/dist-demo`.

## Deploy (free): Render + MongoDB Atlas

1. **MongoDB Atlas:** create a free M0 cluster at mongodb.com/atlas. Add a database user, allow network access from `0.0.0.0/0`, and copy the connection string (add a database name, e.g. `…mongodb.net/portfolio?retryWrites=true&w=majority`).
2. **GitHub:** push this folder to a repo named `portfolio`.
3. **Render:** New → Blueprint → choose the repo. Render reads `render.yaml`. Paste the Atlas string into `MONGODB_URI` when asked.
4. Done. Render builds the React app, and Express serves it plus the API from one URL. `/api/health` should show `"store":"mongo"`.

The free Render plan sleeps after 15 minutes idle, so the first visit after a while takes 30–60 s. The site shows a clear message and a retry button while it wakes.

**Other hosts:** the `Dockerfile` works on Railway, Fly.io or Cloud Run. To host the client on Vercel separately, set `VITE_API_URL` in the client and `CLIENT_ORIGIN` on the server.

## Add a LinkedIn post to the site

After posting on LinkedIn: open the post's “…” menu → **Copy link to post**, go to `https://<your-site>/admin`, enter your `ADMIN_TOKEN` once, paste the link and press **Add post**. It appears at the top of `/posts` straight away.

Why not fully automatic? LinkedIn's permission for reading a member's own posts (`r_member_social`) is closed to new apps, and liking on a visitor's behalf needs a vetted API plus the visitor's own LinkedIn sign-in. So posts are added by link, and likes happen on LinkedIn itself through the buttons under each post.

## Read your messages

```bash
curl -H "Authorization: Bearer <ADMIN_TOKEN>" https://<your-site>/api/admin/messages
```

`ADMIN_TOKEN` is generated by Render; find it under the service's Environment tab.

## API

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/api/health` | Status and which store is active |
| GET | `/api/content` | Profile, projects, experience, certifications, skills |
| GET | `/api/projects` (also `experience`, `certifications`, `skills`) | One collection |
| POST | `/api/contact` | `{ name, email, message }` |
| POST | `/api/events` | `{ type: pageview or query, path?, visitorId }` |
| GET | `/api/stats` | Views, unique visitors, 14-day series, top pages, queries run |
| GET | `/api/posts` | LinkedIn posts shown on `/posts`, newest first |
| POST | `/api/admin/posts` | `{ url }` add a post by its LinkedIn link (Bearer token) |
| DELETE | `/api/admin/posts/:urn` | Remove a post from the site (Bearer token) |
| GET | `/api/admin/messages` | Contact messages (Bearer token) |
